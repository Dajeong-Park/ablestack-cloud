# SP-12 스냅샷 태그 종결 수명주기

일반 삭제와 보관 상한 초과 삭제는 SnapshotManagerImpl의 동일 삭제 경로를 통과한다. 정상 저장소 전략은 최종 논리 스냅샷을 Destroyed로 update하지만 SnapshotDao.remove의 태그 정리를 호출하지 않아 태그가 남는다. UI 변경은 필요하지 않으며 기존 VM 공통 목록·MoldDialog·태그 조작을 유지한다.

삭제 lock 안에서 저장소 작업이 성공한 뒤 별도 종결 검사를 수행한다. 최신 스냅샷이 Destroyed 또는 removed이고, **전체 Zone/전체 사본**이 Destroyed/Hidden으로 종결됐으며, 강제 정리의 pending/unmapped 기록이 없을 때만 ResourceTagDao의 Snapshot 타입·정확한 숫자 ID로 태그를 제거한다. 일부 Zone 성공, 실패·미확인 참조, 강제 DB 정리 후 남은 물리 대상은 태그를 보존한다. Hidden은 자식 체인 때문에 물리 기반을 보존한 논리 삭제 상태이며 활성 논리 스냅샷과 구분한다. 태그 제거 후 같은 ID/타입을 재조회하여 남으면 성공으로 보고하지 않는다. 이미 Destroyed인 자원에 대한 권한 확인된 재시도도 같은 검사로 과거 잔여를 정리한다. 정책 삭제에는 이 루틴을 연결하지 않는다.

태그 추가와 삭제가 경합해 종료 후 태그가 다시 생기지 않도록 Snapshot에 한해 createTags가 동일 snapshot-delete-ID lock을 사용한다. 다중 ID는 고유 숫자 ID 오름차순으로 잠그고 예외·시간 초과·트랜잭션 종료 뒤 모두 해제한다. 기존 ACL 확인 후 Destroyed/removed 스냅샷의 새 태그를 거부한다. 다른 자원 타입과 명시적 deleteTags의 기존 계약은 유지한다. 일반 태그 서비스를 재구현하지 않는다.

집중 검사는 정상·보관 초과 공통 경로, 2개 Zone 중 일부 성공, 물리 실패·예외·이미 종료 재시도, 강제 pending/unmapped, 타입 충돌·다른 스냅샷 보존, 태그 생성 lock/ACL/종료 거부를 다룬다. 31 GFS2·32 RBD에서는 전용 볼륨/태그/정책과 실제 UI, 자연 예약 태그 상속·보관 초과, 실제 물리 삭제 실패·복원·재시도, 정책 삭제 보존, 명시적 태그 삭제·권한을 API/job/DB/Primary·Secondary·trash로 대조한다. 추가 Zone 실물이 없으면 다중 Zone은 집중 검사와 단일 Zone 실제 사본 실패를 구분한다.

전역 용량 임계값 0.90과 기존 Prometheus WAL 보존 링크/대상을 유지한다. 전체 Cloud 빌드·FT 변경·Europa 병합은 수행하지 않는다. 실제 종결 전에 수동 deleteTags로 시험 결과를 가리지 않으며, 실패 진단 자료와 정상 정리 결과를 분리한다.
