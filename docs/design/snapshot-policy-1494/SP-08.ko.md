# SP-08 — 정책 일정·정수·보관 한도 계약

대상 #1502 / 부모 #1494. 기준 HEAD `8749dac4f4f`. 변경 Maven 모듈은 `api`, `server`이며 UI의 공통 `storage/FormSchedule`을 함께 수정한다.

## 서버 입력 계약

일정은 날짜 계산기의 lenient 보정에 맡기지 않고 정책/태그/예약의 쓰기 전에 검사한다. 기존 소유 접근 검사는 유지한다.

| 주기 | 인코딩 | 허용 범위 |
|---|---|---|
| HOURLY | MM | 분 0~59 |
| DAILY | MM:HH | 분 0~59, 시 0~23 |
| WEEKLY | MM:HH:DD | 분/시 동일, 요일 1(일)~7(토) |
| MONTHLY | MM:HH:DD | 분/시 동일, 일자 1~28 |

각 요소는 ASCII 숫자 1~2자리다. `0`/`00` 모두 허용하고 음수·소수·공백·누락·추가 요소·overflow는 거부한다. 주기는 기존 대소문자 무시 계약을 유지한다. 시간대의 기존 Java 호환/정규화 계약은 변경하지 않는다.

보관 수는 API의 INTEGER 타입 검증에 더해 1 이상, 해당 주기의 적용 상한 이하로 검사한다. 적용 상한 0 이하는 등록 불가다. 소유 계정/프로젝트·도메인 제한과 관리자 소유 예외는 기존 서버 계약을 유지한다. 오류는 필드/허용 범위와 수정 방법을 안내하며 Java Volume 객체 전체를 넣지 않는다.

모든 거부는 SP-06의 upsert 트랜잭션에 들어가기 전에 발생한다. 유효하지 않은 재제출이 기존 UUID·정책 값·태그 행·다음 예약을 바꾸지 않는지 독립 DB로 검사한다.

## 현재 적용 한도의 조회

`listCapabilities.capability.snapshotpolicymax`에 `hourly/daily/weekly/monthly` 정수 map을 추가한다. `ListCapabilitiesCmd`가 정책 검증과 같은 `Snapshot.Type.*.getMax()`를 읽는다. 재시작이 필요한 설정의 DB 값과 실제 적용 값이 다를 수 있으므로 UI에서 `listConfigurations` 값을 적용 상한으로 추정하지 않는다. 기존 capability 필드는 유지하며 새 필드는 추가 메타데이터다.

UI는 폼을 열 때 허용된 `listCapabilities`, `listAccounts`, `listResourceLimits`를 읽는다. 계정 이름/도메인 또는 프로젝트 ID를 대상 볼륨에서 가져오고, 응답에서도 같은 소유 범위와 snapshot 유형·untagged 제한인지 확인한다. 일반 사용자의 도메인 제한 요청이 자기 계정 결과로 치환되는 경우 이를 도메인 한도로 사용하지 않는다.

관리자 **소유 계정**의 예외를 확인하면 계정/도메인 제한을 적용하지 않는다. 관리자 호출자가 일반 소유자의 볼륨을 관리하는 경우에는 그 소유자의 제한을 적용한다. 확인된 제한 중 0 이상 값의 최소값으로 보관 수를 검증하고 -1은 해당 소유 한도의 무제한이다. 소유 예외 여부를 확인하지 못하면 그 범위의 값으로 잘못 차단하지 않는다.

권한 부족·실패·누락·잘못된 응답은 확인 불가로 표시한다. 고정 8이나 임의의 무제한으로 대체하지 않는다. 재시도는 초안을 보존한다. 서버는 제출 시 최신 값으로 다시 검사한다. UI는 남은 생성 가능 quota와 정책의 보관 한도를 혼동하지 않게 안내한다.

## 공통 UI와 안전성

컴퓨트 > 가상머신의 AntD 세로 폼·입력/오류·보조 설명·취소/확인 버튼과 테마 토큰을 사용한다. 전역 VM CSS를 변경하지 않는다. 시간/보관 입력은 범위를 벗어난 값을 blur에서 자동 보정하지 않고 정수·범위 검증 결과를 표시한다. 00분은 Number 0으로 그대로 전송한다.

요일은 0~6의 UI 선택을 API 1~7로 변환하고 일자는 Number로 인코딩한다. 폼 검증 직후에도 제출 직전에 최신 값/한도/권한/문맥을 재검사한다. 한도 조회 중에는 중복 제출을 막고 로그인·프로젝트·대상·권한 변경과 언마운트 후의 늦은 응답은 적용하지 않는다. 태그 초안과 서버 실패 후 입력 보존은 SP-04의 계약을 유지한다.

정책 메뉴와 볼륨 탭은 같은 FormSchedule을 사용한다. 동명의 compute/backup/FormSchedule은 별도 컴포넌트이며 변경하지 않는다. 월 일자 검색의 숫자 처리 #1497, 기존 정책 편집/관리자 중지·재개 UI #1499, 삭제 UX #1501은 별도 범위다.

## 검증·배포 계획

변경 API/server 모듈만 WSL ext4에서 빌드하고 일정 경계·거부·applied metadata·공통 폼/태그/조회 실패·소유 범위·중복/늦은 응답을 집중 검사한다. UI lint·production build 후 서버 JAR의 변경 클래스 계열과 정적 자산만 반영한다. 원본 JAR·WEB-INF/META-INF·설정·기존 FTCTL 클래스/변경을 보존한다.

31 GFS2·32 RBD에 전용 1GiB 볼륨과 일반 소유자를 사용한다. 실제 UI의 00/59분·보관 수 오류·한도 안내·실패/수정 재시도와 4개 주기 인코딩을 API/DB와 대조한다. 기존 정책이 0건인 상태에서 적용 상한 3 및 비활성 0을 임시 시험하고, 원래 설정 복원 전후의 적용 값/재시작 계약을 확인한다. 다크/라이트와 390/768/1280px에서 새 설명과 공통 폼을 비교한다.

시험 개체는 정상 API로 정리하고 기존 자원·설정과 별도 dirty FTCTL 작업을 전후 대조한다. 전체 Cloud 빌드·Actions dispatch·qemu 배포·Europa 병합은 이 작업에 포함하지 않는다.

## 실환경 API 차이와 배포 결정

실제 비교에서 31의 대상 클래스는 기준 브랜치와 기존 메서드 바이트코드가 일치했다. 32의 SnapshotManager도 일치하지만, 32의 두 capability 클래스에는 기준 브랜치에 이미 있는 `userdatamaxlength` 필드/호출이 없었다. 이번 변경으로 이 별도 기능까지 추가하지 않도록 32 배포에 한해 두 API 소스에서 해당 기존 필드/호출만 제외한 compatibility overlay를 Maven으로 빌드했다. 패치와 해시를 검증 보고서에 보존하고 작업 트리 소스는 즉시 원복했다. 제품 브랜치에서는 기존 userdata 기능을 유지한다.

양쪽 모두 변경 전 capability 응답에서 `snapshotpolicymax`를 제외한 모든 필드/값이 같은지 검증한다. 새 메타데이터의 적용 값, 정책 입력 검증과 공통 UI 계약은 동일하다. [실행 결과와 한계](../../validation/snapshot-policy-sp08-1502-20261027/README.ko.md)에 배포 차이와 재현 조건을 기록한다.
