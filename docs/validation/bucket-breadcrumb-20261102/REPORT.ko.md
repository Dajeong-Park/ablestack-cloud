# 버킷 breadcrumb와 대화상자 구조 표준 준수 개선

2026-11-02 Asia/Seoul. PR #1541 병합 후 추가 확인한 버킷 목록 헤더 및 대화상자 구조를 수정했다. 같은 Europa 기준의 별도 `dhslove/bucket-breadcrumb-standard` 브랜치에서 UI만 변경했다.

## 원인과 구현

- 버킷 목록의 저장소 필터가 공통 breadcrumb 컨트롤 슬롯 밖의 독립 행에 있어 VM 목록보다 헤더 높이가 커졌고, 텍스트 업데이트 버튼이 중복됐다.
- 필터를 공통 breadcrumb의 필터/프로젝트 영역으로 옮기고 VM 필터와 같은 작은 선택기·필터 아이콘을 사용한다. 접근성 라벨은 유지하고 선택 목록 업데이트는 tooltip/aria-label이 있는24px 원형 보조 아이콘으로 제공한다. API 필터·프로젝트·조회 generation 계약은 바꾸지 않았다.
- 버킷 목록에만 모바일 breadcrumb 여백과 작업/검색 줄바꿈을 적용했다. 기본 VM 목록과 버킷 상세에는 이 목록 전용 배치가 적용되지 않는다.
- 기존 다크 트랙과 손잡이 배경이 유사해 프로젝트 스위치 손잡이 대비가 약1.08:1이었다. 목록 breadcrumb의 손잡이에 테마 토큰을 적용하고 선택 상태도 구분한다. 활성 본문 대비4.5:1, 상태 손잡이 대비3:1 이상을 확인한다.

- 버킷/오브젝트 스토리지 액션 창은 일반 a-modal에서 Footer를 없애고 폼 내부에 취소/확인 버튼을 넣고 있었다. 공통 MoldDialog md 크기와 MoldDialogActions Footer 연결을 사용해 제목은 Header, 최종 액션은 Footer, 스크롤은 본문으로 한정한다.
- 버킷 생성·업데이트·키 관리·삭제/강제 정리, 저장소 추가·수정·키 교체·삭제에 적용했다. 키 교체/복구의 최종 작업도 Footer에 놓고, 데이터 조회 등 컨텐츠 내 보조 버튼은 해당 컨텐츠에 둔다. 업로드·폴더·보호/버전 확인 창은 기존 명시적 Header/Footer를 실제 화면에서 검증한다.
- 폼 @click 제출 및 validation을 유지하고, API 처리 중 Footer의 busy 상태가 Header 닫기/ESC에 전달된다. 실패 시 입력값 유지와 재시도, unmount 시 Footer 정리를 실제 폼을 포함한 회귀 검사로 확인한다. 대화상자별 generation key와 1개 캐시로 이전 폼 액션이 다음 창에 남지 않게 한다.

## 실제 UI 검증

31/32 × light/dark × 360/768/1280px **12뷰**를 최종 앱에서 검증했다. 선택기가 breadcrumb 안에 있고 독립 필터 행은0개다. 활성 본문 최소 대비4.93:1, 기본 프로젝트 손잡이 최소 대비12.32:1이며 선택 상태도 별도 검사했다. 컨트롤 가로 넘침0, 키보드 포커스·보조 아이콘 라벨을 확인했다. 기본 VM 목록과 버킷 상세에는 목록 전용 필터가 없음을 확인했다.

동일1280×900에서 헤더 높이 145.00→117.00px, 360×900에서 253.00→223.00px. 실제 viewport와 원본 JPEG 디코딩 크기를 대조했으며 JSON의 개별 좌표를 함께 보존했다.

32번에서 저장소 UUID 필터 선택·선택 목록 업데이트·검색 일치1건/미일치0건·조건을 유지하는 주 업데이트·breadcrumb 초기화를 실제 UI로 확인했다. 프로젝트 스위치를 켜고 끈 뒤 원래 범위로 복귀했고, 선택한 버킷의 만들기/빈 버킷 삭제 버튼은360px에서 같은 행에 겹치지 않게 표시됐다. 삭제 확인 창은 열고 취소했다. 필터에서 Tab으로 이동하면 보조 업데이트 아이콘에 포커스가 도착하고 접근성 라벨이 유지된다.

31번은0버킷/0저장소의 빈 목록에서 선택 목록 업데이트·프로젝트 전환과 생성 창의 저장소 없음/확인 비활성 상태를 확인했다. 32번 생성 창의 Footer 확인 버튼은 빈 이름·할당량 유효성 오류를 표시하고 창을 유지했으며 API 생성은 수행하지 않았다. VM 목록의 양쪽 테마에서 공통 breadcrumb 및 모든 컨트롤 스타일이 전후 동일하고, 버킷 상세에는 목록 전용 필터/클래스가 없음을 확인했다.


31/32의 실제 화면에서 대화상자 **27개 조건**을 검증했다. 32번은 생성·업데이트·키 관리·삭제/강제 정리 및 저장소 추가·수정·키 교체·삭제의 라이트1280px/다크360px, 업로드 양쪽 테마, 폴더·버전·그룹 삭제 확인 창을 포함한다. 31번은 생성·저장소 추가 창의 라이트1280px/다크360px를 확인했다.

모든 창에서 제목은 Header, 최종 버튼은 Footer에 있고 본문 내부의 기존 action-button 그룹은0개였다. 긴 생성·확장된 업데이트·업로드 폼 등 **7개 조건**은 실제 휠 입력으로 본문의 scrollTop만 바뀌고 Header/Footer 좌표·바깥 wrap·페이지 스크롤은 유지됐다. 샘플링한 활성 제목·라벨·버튼의 최소 텍스트 대비는 **4.67:1**이었다. 업로드는 한글·공백 값이 있는 메타데이터8행(전송568B)을 입력해 배치·가독성과 고정 Footer를 확인하고 취소했다. 파일은 올리지 않았다. 키는 명시적으로 조회/교체하지 않았고, 삭제·강제 정리·저장소 삭제의 최종 실행은 하지 않았다.

공통 모바일 테마 전환 지연은 별도로 재현했다.360px에서 라이트 선택 후에도 body.dark-mode와 어두운 배경이 유지되고1280px 전환 후 적용됐다. 이는 Logo의 테마 watch/mounted 의존성과 모바일 SideMenu 미생성 경로에 관련된 별도 범위이며, 본 수정에는 포함하지 않았다. 각 최종 검증 파일의 실제 테마 클래스·색상을 확인해 선택값만으로 다크모드 통과를 판단하지 않았다. [재현 자료](evidence/ui/followup-mobile-theme.json)를 다음 공통 UI 작업의 기준으로 남긴다.
