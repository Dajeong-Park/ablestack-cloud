# #1520 VM 복제 배치 결과 및 재시도 설계

## 계약

기존 `cloneVirtualMachine` 비동기 Job과 단일 `UserVmResponse`를 유지한다. 성공 응답에는 마지막 VM 필드와 함께 `clonebatch`를 추가한다. 실패한 Job을 성공으로 바꾸지 않는다. 실패·응답 유실의 전체 결과는 `queryVMCloneBatch(requestid)`로 조회한다.

최초 요청의 `customjobid`는 배치 UUID이며 생략한 기존 호출에는 서버가 UUID를 발급한다. UI는 POST 전에 UUID와 원래 입력을 브라우저에 저장한다. 동일 UUID·동일 입력의 재전송은 기존 Job을 반환한다. 배치 UUID를 다른 입력에 재사용할 수 없다.

재시도는 최초 `batchid`, 새로운 `customjobid`, 원래 1부터 시작하는 `retryindices`를 보낸다. 원래 count와 이름을 유지하므로 2번만 재시도해도 이름은 `이름-2`이다. API 접수는 배치별 전역 잠금, 실행은 배치 및 원본별 잠금으로 직렬화한다.

## 기록과 조회

`vm_clone_batch`에 계정/원본/입력 지문/원래 대상 목록/시도-Job 연결/VM 및 볼륨 체크포인트를 저장한다. 범용 VM 상세 값에 넣지 않는다. 볼륨 UUID는 DB 할당 및 스토리지 명령 전에 기록한다. 각 VM 생성과 DATA 연결 완료 후 생성 여부를 기록하고 시작 단계를 별도로 기록한다.

조회는 현재 VM·볼륨 상태와 권한으로 결과를 다시 구성한다. 원본 소유권이 달라졌거나 접근 권한이 없으면 식별 정보를 제외한 NOTFOUND를 반환한다. 대상 접근 권한이 달라졌다면 해당 UUID·볼륨·원래 오류를 숨긴다. 전체 오류도 숨긴다. 브라우저에는 이전 결과 UUID를 저장하지 않는다.

정리 상태는 `not-created`, `preserved`, `prepared`, `pending`, `removed-in-cloud`, `unconfirmed`로 구분한다. `removed-in-cloud`는 DB상 Expunged 및 removed 확인이며 독립적인 물리 삭제 보증으로 표시하지 않는다. Destroy/Expunging은 정리 완료가 아니다.

## 대상별 재시도

| 동작 | 허용 조건 | 처리 |
| --- | --- | --- |
| CREATE | 성공 생성 이력이 없고 기존 계획 볼륨이 모두 제거되었으며 원본 디스크·위치·형식·할당 의도·오퍼링이 동일 | 실패 또는 미시도 대상만 재시도 시점 원본으로 새로 복사 |
| RESUME | 같은 GFS2 작업의 준비 완료 디스크와 원본 작업 메타데이터가 일치 | 준비된 디스크로 VM 생성/남은 DATA 연결부터 진행 |
| START | 모든 계획 디스크가 연결된 기존 Stopped VM, 시작 요청이 있었음 | 같은 VM 시작만 수행 |
| NONE | 성공 대상, 삭제된 성공 대상, 권한 변경, 준비/정리 불명확, 원본 변경 | 자동 재생성 차단 및 점검 안내 |

시작 실패 후 기존 VM/디스크를 유지한다. 생성 완료 대상의 시작은 신규 배포 전용 롤백 경로 대신 일반 시작 경로를 사용한다. 재시도 대상 이름은 `getHostName()`으로 대조한다. `getName()`은 사용자 지정 이름이 아닌 내부 인스턴스 이름이다. GFS2 준비 후 중간 생성 실패는 알려진 준비 디스크를 유지한다. 준비 명령의 결과 자체가 불명확하면 원본 보호 장벽을 유지하고 재시도를 허용하지 않는다. 정상 RBD Linked 및 GFS2 backing/flatten 수명주기를 유지한다.

Job 종료 직전 체크포인트가 유실되면 기록된 볼륨과 실제 연결을 대조해 생성 이력을 복구한다. 중단된 시도가 불명확한 경우에는 자동 재실행하지 않는다. 서버 강제 종료 후 계속 실행되는 복사 작업을 완료로 추정하지 않는다.

## UI

복제 폼을 전체 결과 표로 전환한다. 요청/Job ID, 전체 대상 이름·UUID·생성/시작 단계·오류·볼륨 및 정리 상태와 상세 링크를 표시한다. 활성 Job은 조회하고, 모달을 다시 열면 저장한 식별자로 복구한다. 접수 여부가 불명확하면 동일 요청 재전송만 허용한다. 성공 대상은 실패 재시도 목록에 포함하지 않는다. 조회 중에는 요청 전환을 막고 늦게 도착한 다른 요청의 결과를 버린다. 상세 링크는 모달을 종료한다. 복제 접수·조회는 `preserveOnFailure` 옵션을 사용해 통신 장애 때 기존 결과와 로그인 세션을 보존하고 실제 401 인증 실패는 기존 처리기로 전달한다.

실환경 DATA 복사 실패 주입에서 물리 이미지가 없는데 soft-removed 볼륨이 `Expunging`에 남는 별도 문제를 확인했다. #1520은 이를 `pending`으로 표시하고 재시도를 차단한다. 자동 정리와 원인 오류 개선은 Epic 하위 #1524로 추적하며, 이 상태를 정리 성공으로 숨기지 않는다.

## 적용 및 검증 경계

WSL ext4에서 변경 API/schema/server 모듈만 빌드한다. 테스트 환경은 이미 배포된 #1518/#1519와 통합해 검증하며, PR의 기존 정책·정리 보호는 유지한다. 전체 Cloud/Release 빌드는 실행하지 않는다.

DB 마이그레이션은 idempotent 신규 테이블이다. 테스트 서버에는 해당 DDL과 신규 DAO/관리자 빈만 반영하고, 기존의 다른 업그레이드 단계를 임의 실행하지 않는다. JAR 및 정적 UI 배포는 기존 항목/WEB-INF/설정을 보존하고 백업·해시·HTTP·런타임을 검증한다.

22번 `rocky98-perftest`와 연결 디스크는 모든 변경 대상에서 제외한다. PID/startTicks 및 API/DB 메타데이터만 읽어 전후 상태를 대조한다. 실패 주입과 삭제는 `qa1520-*` 전용 자원으로 제한한다.
